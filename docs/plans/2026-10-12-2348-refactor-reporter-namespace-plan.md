# Reporter Namespace (Grab-Bag Unit U9) - Plan

## Goal Capsule

- **Objective:** adding a built-in reporter is its module family plus one registration entry.
- **Means:** move the built-in reporter modules into `packages/stryker-js/src/Reporter/`, replace the `builtin` record and `reporter-factories.ts` with a typed `BuiltinReporter` list in the `Reporter` layer, give sarif its own cell, and make stdout membership command data for `planReporters`.
- **Authority:** unit U9 of `docs/plans/2026-10-12-1732-refactor-grab-bag-decomposition-plan.md` (carried by #317, not yet on `main`), refreshed against `main` ec1769de2. This plan replaces that section for U9 only; every other unit and decision of the parent plan stands.
- **Delivery:** one PR off `main`, as the operator directed for U9 (intent r40). Shared files with other open PRs are listed in Q10 and in the PR body; Stream A merges U9 up, as the parent brief arranges.

## Product Contract

### Requirements (carried from the parent plan; R11, R14 and R15 restated for U9)

- R3. No new module shares mutable state with another or reaches another through a re-export.
- R11. Built-in reporters form one capability in `packages/stryker-js/src`. Adding one means adding its module family plus one registration entry, with no edit to name schemas, factory tables, failure mappers or `plan-reporters.workflow.ts`.
- R12. A reporter's name, its failure mapping and whether it writes to stdout are declared once, and every consumer (config validation, `planReporters`, the factory table) derives from that declaration.
- R13. Plugin-loaded `'Reporter'` descriptors and the host-supplied `html` reporter resolve by name exactly as today.
- R14. Exit codes, log lines, stdout records, report files and the stream protocol are unchanged; every span on `main` keeps its name, attributes and ancestors; a new span is a new `SpanTaxonomy` entry mirrored in `contract/span-taxonomy.json` with a cli-contract changeset.
- R15. A decision that moves or changes in a workflow gets laws in `src/__tests__/<stem>.workflow.property.test.ts` that can fail on a plausible bug, and the PR cites the surviving-mutant ids they target from the latest `main` Mutation report.
- R18. The PR covers one capability, branches from `main`, carries changesets for the packages it changes, merges `main` in when `main` moves and never rebases.

### Acceptance

- AE1. Given a new built-in reporter `foo` that writes `reports/foo.txt`, when a developer adds its module family (a workflow declaring its name literal, and a cell) and its entry in the `Reporter` registry, then `reporters: ['foo']` validates, `planReporters` places it correctly, `foo` receives every `ReporterEvent`, and the only existing file that changes is `Reporter/reporter.service.ts` (one import and one list entry). Checked by review: the PR body shows that diff; no reporter is added.
- AE2. Machine-mode plans keep the configured names that are not stdout reporters, in configured order and with repeats kept, and append `progress-stream` only when the filtered list lacks it; human-mode plans map `progress-stream` to `clear-text` and keep first occurrences in order. Exactly as on `main`.

## Planning Contract

### Key Technical Decisions

- **D1. `src/Reporter/` is a feature folder of flat suffixed files with no `mod.ts`** (Q8). Consumers import leaf modules. `Rerun/mod.ts` and `Survivors/mod.ts` are unpublished barrels on `main`; this plan does not extend that pattern.
- **D2. The registry is `readonly BuiltinReporter[]` on the `Reporter` service** (`BuiltinReporter { name, stdout, factory }`), built in `Reporter/reporter.service.ts`'s layer. A module-scope `fromReportCell(cell, context)` in the same file turns a one-pass report cell into a factory and serves json, clear-text and sarif; progress keeps its per-event fold (moved unchanged, same two spans) as its entry's factory. The progress-stream drain's failure name is `ProgressReporterName.literal`, so the emitted value stays `'progress'`. The drain entry is `stdout: false`: marking it would make machine mode collapse a repeated configured `progress-stream` (Q5). `prepare.ts` reads `Reporter` before planning and derives the stdout names and the choice table from the list; host entries still override by name (R13).
- **D3. Names are declared once.** `progress-stream` and `clear-text` are `MachineStreamRole` and `HumanStreamRole` in `Reporter/reporter-role.schema.ts`. `json`, `progress` and `sarif` are literal schemas exported by each family's workflow file. Each cell builds its private `ReporterFailed` mapper by passing its name to `failAsReporter` in `Reporter/reporter-failed.ts`, which holds no names; `reporter-failures.ts` and `reporter-name.schema.ts` go.
- **D4. `ReporterPlanCommand` gains `stdout: S.Array(S.String)`.** `STDOUT_REPORTERS` goes; the roles come from the role schema.
- **D5. Sarif gets `Reporter/sarif-report.cell.ts`** under a new span `stryker.report.sarif`. Whether a report arrived is a tagged variant, not an optional field (pack: schema-laws, `tagged-unions-over-state-by-presence.md`): `SarifReportCommand.reported` is `SarifReported { report, survivors } | SarifNotReported {}` (Q10), the read builds it with `Stream.runFold` seeded with `SarifNotReported` (Q9), and `sarifReport` dispatches with `Match.tag` to its outcomes, a new `SarifReportSuppressed` for `SarifNotReported`.
- **D6. Files move with `git mv`**, keeping stems, so each property test keeps its stem. `render-clear-text-report.workflow.ts` moves too; U11 rewrites it in place.
- **D7. The two moved services take path-derived keys** (Q12): `@systemfsoftware/stryker-js/Reporter/reporter.service/Reporter` and `.../Reporter/reporter-output.service/ReporterOutput`. Both are package-internal.
- **D8. Changesets:** cli-contract `minor` for the added span, following #277's `rpc.typeQuery` precedent; stryker-js `patch`.

### Test Scenarios

- `planReporters`: one law, `∀c_RolesAndStdoutConfigured_≡ReferencePlanForMode`, over the production schemas `ReporterPlanCommand` and an array of `MachineStreamRole | HumanStreamRole`. Each draw's configured list is the drawn names, then the drawn roles, then the drawn stdout names, so every draw reaches the stream mapping, the deduplication and the stdout filter. The oracle is a loop-written reference of AE2, not the code's `Array.dedupe`/`filter` chain. Fails if a stdout name survives, the stream is appended twice or dropped, `progress-stream` is not mapped in human mode, duplicates stay in human mode or are removed in machine mode, or order changes.
- `sarifReport`: the four existing laws draw `SarifReported` commands; a fifth, `∀c_SarifReportCommand_≡SuppressedIffNotReported`, draws a command and a boolean that swaps in `SarifNotReported`.
- No new integration test.
